1. Постановка задачи

ML-модель может продолжать технически корректно выдавать прогнозы, когда распределение production-данных уже отличается от обучающей выборки. Такое изменение способно незаметно снизить качество модели и создать бизнес-риски. Задача проекта — автоматически обнаруживать нарушения целостности данных, локальные сдвиги признаков и изменение структуры данных в целом.

Reference

Зафиксированная историческая выборка, относительно которой оцениваются новые данные.

Current

Текущий батч либо окно production-событий, передаваемое в общий pipeline.

Результат

JSON-безопасный словарь с качеством, метриками, порогами, статусами и алертами.

Data drift описывает изменение P(X). Concept drift означает изменение P(y|X). Без фактических ответов основной модели статистика входов не доказывает concept drift, поэтому система формирует сигнал для расследования, а не автоматическую команду на переобучение.

2. Архитектура решения

Все интерфейсы используют одну реализацию analyze(reference, current, config). CLI, HTML, Streamlit и Online API не дублируют статистику и не меняют смысл результата.

2 · SchemaКолонки и типы
3 · QualityNaN, дубликаты, диапазоны
4 · DriftKS, W₁, χ², PSI, JS
5 · MLOOF Adversarial Validation
6 · AlertsПороги и объяснения
7 · ContractAnalysisResult 0.2
8 · InterfacesCLI, HTML, UI, API

Online-контур

FastAPI принимает события и готовые батчи. События накапливаются в непересекающихся count-based окнах, после чего становятся Current для общего pipeline. SQLite хранит Reference, буфер, Run, результаты, алерты, доставки и Feedback. Streamlit читает это состояние без повторного анализа.

Идемпотентность

Повтор идентичного event/batch возвращает прежний результат; конфликт получает HTTP 409.

Persistent state

SQLite WAL и Docker volume сохраняют Reference и историю после рестарта.

Доставка

JSONL и необязательный webhook имеют отдельные статусы и повторные попытки.

Feedback

Запаздывающий y_true позволяет считать Accuracy и ROC-AUC основной модели.

8. Ограничения и дальнейшее развитие

  • Демонстрационные пороги требуют повторной калибровки на истории конкретного источника.
  • SQLite-реализация рассчитана на один API worker и локальное persistent-хранилище.
  • API не содержит TLS, аутентификацию, авторизацию и rate limiting.
  • Kafka, Redis/Celery, горизонтальное масштабирование и автоматическое переобучение не входят в прототип.
  • Reference не заменяется автоматически: его обновление является явным решением оператора.
  • Delayed Feedback показывает деградацию качества, но не устанавливает причинный механизм concept drift.

Вывод

Разработан воспроизводимый пайплайн, закрывающий требования к Data Quality, статистическим drift-метрикам, Adversarial Validation, единому интерфейсному контракту, визуализации и online-мониторингу. Контрольный сценарий остаётся стабильным, а намеренно внесённые числовой, категориальный и missingness-сдвиги формируют объяснимые алерты.
