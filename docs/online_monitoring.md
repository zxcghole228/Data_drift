# Контракт online-мониторинга

Статус: проектирование версии `0.3`. Этот документ фиксирует поведение до
начала реализации. Статистическое ядро и формат `AnalysisResult` версии `0.2`
остаются без изменений.

## Цель и границы

Online-слой принимает production-события или уже сформированные батчи,
накапливает события в устойчивые окна и передаёт каждое готовое окно в
существующий `analyze(reference, current, config)`. Результат сохраняется в
истории и может породить уведомление.

Метрики дрейфа не рассчитываются для одной строки. В версии `0.3` поток
обрабатывается **непересекающимися окнами фиксированного размера** (count-based
tumbling windows). Это даёт near-real-time micro-batch мониторинг: данные
поступают непрерывно, а решение появляется после заполнения очередного окна.

В обязательный объём входят:

- HTTP-приём отдельных событий и готовых батчей;
- явный жизненный цикл Reference;
- постоянный буфер и история запусков в SQLite;
- защита от повторной обработки запросов;
- запуск общего pipeline без повторной реализации метрик;
- сохранение и доставка алертов;
- просмотр состояния и истории через API и Streamlit;
- необязательный приём запаздывающих фактических ответов модели.

В версию `0.3` не входят Kafka, Redis, Celery, автоматическое переобучение,
автоматическая замена Reference и горизонтальное масштабирование сервиса.
Границы адаптеров должны позволять добавить их позже без изменения
статистического ядра.

## Термины

| Термин | Значение |
| --- | --- |
| Reference | Зафиксированная базовая выборка, с которой сравниваются новые данные. |
| Event | Одна production-запись с уникальным `event_id` и набором признаков. |
| Window | Непересекающийся набор последовательных событий, используемый как Current. |
| Batch | Готовая Current-таблица, переданная одним запросом и не попадающая в событийный буфер. |
| Run | Одна попытка анализа Window или Batch относительно конкретной версии Reference. |
| Feedback | Запаздывающий фактический ответ `y_true`, связанный с ранее принятым событием. |

## Архитектурное правило

Online-слой отвечает только за приём, накопление, идемпотентность, хранение и
доставку результата. Проверки схемы, Data Quality, drift-метрики, Adversarial
Validation и формирование `AnalysisResult` выполняются только существующим
pipeline. Streamlit и API читают сохранённый результат и не пересчитывают
метрики самостоятельно.

## Конфигурация

Online-настройки добавляются отдельной верхнеуровневой секцией и не изменяют
семантику offline-конфигурации:

```yaml
online:
  enabled: true
  state_path: data/online/monitoring.sqlite3
  window:
    strategy: tumbling
    size: 500
    min_batch_rows: 100
  alerts:
    jsonl_path: outputs/online/alerts.jsonl
    webhook_url_env: DDG_ALERT_WEBHOOK_URL
    timeout_seconds: 5.0
    max_attempts: 3
  performance:
    enabled: false
    min_feedback_rows: 100
    baseline_accuracy: null
    max_accuracy_drop: null
    baseline_roc_auc: null
    max_roc_auc_drop: null
```

Analysis-секция `configs/online.yaml` использует отдельный Wasserstein-порог
`3.0` только для `age`. Общий Wasserstein-порог и решение для `income`
отключены через `null`, поскольку метрика измеряется в единицах конкретного
признака и порог в годах нельзя применять к денежному доходу.

Правила конфигурации:

- `window.strategy` в версии `0.3` принимает только `tumbling`;
- `window.size` — положительное целое число;
- `min_batch_rows` — положительное число, не превышающее `window.size`;
- каталог базы и JSONL создаётся сервисом, но родительский путь должен быть
  доступен на запись;
- URL webhook не хранится в YAML и читается только из указанной переменной
  окружения;
- секция `online` необязательна для CLI и обычного Streamlit-анализа;
- неизвестные ключи и противоречивые значения завершают запуск понятной
  ошибкой конфигурации.

## Жизненный цикл Reference

Reference регистрируется явно из CSV или Parquet. При регистрации сохраняются:

- сгенерированный `reference_id`;
- пользовательское имя;
- SHA-256 исходного файла;
- SHA-256 эффективной конфигурации;
- формат, число строк, список колонок и pandas-типы;
- время создания и признак активности.

Одновременно активна ровно одна версия Reference. Она не заменяется
автоматически данными Current. Все Run содержат `reference_id`, поэтому старые
результаты остаются воспроизводимыми после смены базы.

Активация новой версии при непустом событийном буфере по умолчанию запрещена.
Оператор должен дождаться полного окна либо явно подтвердить очистку остатка;
очистка записывается в аудит. Это исключает окно, случайно собранное относительно
двух разных Reference.

## Приём событий и окна

Минимальный envelope события:

```json
{
  "event_id": "order-000001",
  "occurred_at": "2026-09-23T10:15:00Z",
  "features": {
    "age": 34.0,
    "income": 72000.0,
    "region": "central"
  },
  "prediction": 1,
  "score": 0.81
}
```

`prediction` и `score` нужны только для будущей проверки качества модели и
не передаются в drift-признаки, если они не объявлены в схеме явно.

События получают монотонный номер при записи в SQLite. После накопления
`window.size` ещё не обработанных событий сервис атомарно:

1. закрепляет первые `window.size` строк за новым Window;
2. строит Current DataFrame только из `features`;
3. запускает общий pipeline относительно активного Reference;
4. сохраняет полный JSON-результат и сводные поля Run;
5. помечает события обработанными;
6. формирует задания доставки для появившихся алертов.

Лишние события остаются началом следующего окна. Неуспешный анализ сохраняется
как Run со статусом `failed` и диагностикой; он не изображается успешным и не
теряется из истории.

Готовый Batch анализируется сразу и не смешивается с событийным буфером. Batch
меньше `min_batch_rows` отклоняется до запуска статистики.

## Идемпотентность

- `event_id` обязателен и уникален за всё время жизни базы;
- `batch_id` обязателен и уникален для готовых батчей;
- повтор идентификатора с тем же SHA-256 нормализованного payload возвращает
  ранее созданное состояние и не запускает анализ повторно;
- повтор идентификатора с другим payload возвращает HTTP `409 Conflict`;
- транзакция создания Window не позволяет двум запросам забрать одни события;
- API не обещает exactly-once доставку по сети, но обеспечивает exactly-once
  обработку внутри одной базы при повторных запросах клиента.

## Постоянное состояние

SQLite является источником истины для одной инсталляции. Минимально хранятся:

- версии Reference и активная версия;
- принятые события и их состояние;
- готовые батчи и их content hash;
- Window и Run;
- полный `AnalysisResult` в JSON;
- алерты и попытки их доставки;
- prediction/score и полученный Feedback;
- служебные события смены Reference и очистки буфера.

Запись Run и перевод входных строк в обработанное состояние выполняются одной
транзакцией. Для SQLite включается foreign key enforcement; режим WAL можно
использовать для одновременного чтения dashboard. Версия `0.3` запускает один
API worker: несколько процессов поверх одного файла SQLite не входят в
поддерживаемый режим.

## HTTP API версии 1

Префикс API: `/api/v1`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /health/live` | Процесс запущен. |
| `GET /health/ready` | Конфигурация валидна, база доступна, активный Reference существует. |
| `POST /references` | Зарегистрировать CSV/Parquet Reference. |
| `POST /references/{reference_id}/activate` | Явно активировать зарегистрированную версию. |
| `GET /references/current` | Получить метаданные активного Reference. |
| `POST /events` | Принять одно или несколько событий. |
| `POST /batches` | Немедленно проанализировать готовый Current batch. |
| `POST /feedback` | Записать запаздывающий `y_true` для принятых событий. |
| `GET /runs` | Получить страницу истории с фильтрами статуса и времени. |
| `GET /runs/{run_id}` | Получить envelope Run и полный `AnalysisResult`. |

Ответ `POST /events` содержит число новых и повторных событий, текущий размер
буфера и список созданных `run_id`. Сервис возвращает `202`, если данные только
попали в буфер, и `201`, если запрос создал хотя бы один Run.

Общие коды ошибок:

- `400` — неподдерживаемый формат или некорректное тело;
- `409` — конфликт idempotency key или запрещённая смена Reference;
- `413` — превышен настроенный размер запроса;
- `422` — данные не проходят схему или online-конфигурацию;
- `500` — непредвиденная внутренняя ошибка с безопасным идентификатором
  инцидента, без traceback в HTTP-ответе.

## Формат Run

Online-envelope не меняет вложенный контракт анализа:

```json
{
  "online_contract_version": "1.0",
  "run_id": "run_...",
  "source": "window",
  "source_id": "window_...",
  "status": "completed",
  "reference_id": "ref_...",
  "config_sha256": "...",
  "row_count": 500,
  "created_at": "2026-09-23T10:20:00Z",
  "completed_at": "2026-09-23T10:20:02Z",
  "analysis_result": {
    "contract_version": "0.2"
  },
  "error": null
}
```

Допустимые статусы Run: `running`, `completed`, `failed`. JSON обязан проходить
`json.dumps(..., allow_nan=False)`.

## Алерты и доставка

Каждый алерт всегда сохраняется в SQLite. Дополнительно сервис может:

- дописать одну JSON-строку в локальный audit-файл;
- отправить POST webhook с `run_id`, Reference, summary и списком алертов.

Webhook имеет ограниченный timeout и до `max_attempts` попыток с задержкой.
Неуспешная доставка не меняет успешный Run на `failed`: её статус и последняя
ошибка сохраняются отдельно и видны оператору. Повторная доставка использует
стабильный `delivery_id`, чтобы получатель мог обеспечить идемпотентность.

## Feedback и concept drift

Data Quality, статистические тесты и Adversarial Validation обнаруживают
изменение входных данных, но не доказывают изменение зависимости `P(y|X)`.
Поэтому система не называет высокий PSI или adversarial ROC-AUC подтверждённым
concept drift.

Если production-клиент передаёт prediction/score, а позднее `y_true`, сервис
связывает Feedback по `event_id` и на заполненном окне считает:

- accuracy, если доступны метки и предсказанные классы;
- ROC-AUC, если задача бинарная и доступны числовые scores обоих классов.

При настроенном baseline падение метрики больше допустимого порога создаёт
отдельный алерт `performance_degradation`. Это практический сигнал возможного
concept drift и повод для расследования, но не причинное доказательство.
Отсутствие достаточного Feedback обозначается `not_evaluated`, а не зелёным
результатом.

## Безопасность и эксплуатационные ограничения

Учебная версия по умолчанию слушает `127.0.0.1`, не реализует пользователей,
TLS и разграничение ролей. Для внешнего production-развёртывания API должен
находиться за reverse proxy/API gateway с TLS, аутентификацией, лимитами тела и
rate limiting. Секрет webhook передаётся только через переменную окружения и не
попадает в отчёты или логи.

## Критерии приёмки

Online-слой готов, когда автоматический сценарий подтверждает следующее:

1. Reference регистрируется, активируется и имеет воспроизводимые метаданные.
2. События переживают рестарт до заполнения окна.
3. Ровно `window.size` событий создают один Run.
4. Сценарий `none` не создаёт drift-алерт, а `combined` создаёт ожидаемые алерты.
5. Повторный event/batch не создаёт новый Run; изменённый повтор получает `409`.
6. Run содержит версию Reference, hash конфигурации и полный `AnalysisResult`.
7. История доступна после рестарта API.
8. Ошибка webhook не уничтожает результат, а успешная доставка аудируется.
9. При включённом Feedback падение качества создаёт performance-алерт.
10. API и Streamlit запускаются через Docker Compose с постоянным volume.
