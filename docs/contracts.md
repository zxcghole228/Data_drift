# Общий контракт, версия 0.1

Это стартовый контракт для согласования 07.09. Изменения должны одновременно отражаться в этом файле, `contracts.py`, конфигурации и использующих их модулях.

## Вход

```python
analyze(reference: pandas.DataFrame,
        current: pandas.DataFrame,
        config: Mapping[str, Any] | None = None) -> AnalysisResult
```

Первые два аргумента обязательны. Конфигурация задаёт ожидаемые колонки, семантические типы, диапазоны и пороги. При `config=None` будущая реализация использует явно документированные значения по умолчанию и схему, полученную только из Reference. Текущая заглушка анализ не выполняет.

- Reference и Current могут иметь разное число строк.
- Строки не сопоставляются по индексам; это сравнение распределений.
- Входные объекты не изменяются.
- Дублирующиеся названия колонок и пустые выборки должны получать явное описание ошибки.
- Неверный Python-тип входа — `TypeError`; неверная конфигурация — `ValueError`.
- Проблемы содержимого допустимого DataFrame возвращаются в структурированном отчёте. Неприменимые вычисления помечаются `skipped` с причиной.

Точные правила преобразования nullable-типов и категорий нужно согласовать в первый день; автоматическое молчаливое приведение типов не допускается.

## Результат

`AnalysisResult` — обычный словарь Python с объявлениями `TypedDict`. Он должен сериализоваться через `json.dumps(result, allow_nan=False)`. Значения NaN/Infinity в выходном JSON заменяются на `None` вместе с объяснением; числовые скаляры numpy переводятся в обычные типы Python.

| Поле | Содержание |
| --- | --- |
| `contract_version` | Строка `0.1` |
| `metadata` | Число строк выборок и seed |
| `schema` | Статус, отсутствующие/лишние колонки и несовпадения типов |
| `quality` | Проверки уровня таблицы и отдельных признаков |
| `drift` | Результаты по признакам и использованные методы |
| `adversarial` | Статус, ROC-AUC, значения по фолдам, важности и объяснение |
| `alerts` | Список сработавших правил: источник, признак, проверка, серьёзность, текст |
| `summary` | Общий статус, количество алертов, проверенных и пропущенных признаков |

`CheckResult` содержит `name`, `status`, `value`, `threshold`, `p_value`, `adjusted_p_value`, `alert`, `reason`, `details`. Для числовой метрики без p-value это поле равно `None`. В `details` помещаются размеры выборок, границы бинов и другие сведения, нужные для проверки расчёта.

## Значение статусов

| Статус | Значение |
| --- | --- |
| `ok` | Проверка выполнена; если правило задано, оно не сработало |
| `warning` | Сработало предупреждение |
| `critical` | Сработало критическое правило |
| `skipped` | Проверку не выполняли или она неприменима; причина обязательна |
| `error` | Проверку не удалось выполнить из-за ошибки; причина обязательна |

`alert=True` — правило сработало; `False` — применимое правило проверено и не сработало; `None` — решения по правилу нет, например не задан порог или проверка пропущена. Отсутствие решения нельзя считать подтверждением стабильности.

Статистические результаты и Data Quality имеют отдельные разделы. Увеличение доли пропусков считается в процентных пунктах: рост с 2% до 7% равен 5 п.п.

Для сводки приоритет состояний: `error`, `critical`, `warning`, затем `ok`. Если ничего не проверено, `skipped`. Частичные пропуски сохраняются в счётчике и пояснениях независимо от общего статуса. `has_alerts` означает только наличие сработавших правил, а не полноту анализа.

## Стартовая конфигурация

`configs/default.yaml` — пример для синтетических данных, а не универсальная схема произвольного датасета. Пороги качества иллюстративные. Незаданные пороги расстояний и ROC-AUC имеют значение `null`: соответствующие численные результаты можно вычислить, но флаг дрейфа без правила выставлять нельзя.

Отдельные типы конфигурации и её runtime-валидацию команда уточняет 07.09. Декларации `TypedDict` сами по себе не выполняют runtime-валидацию результата; она проверяется при интеграции.
