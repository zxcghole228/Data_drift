## Инженерный путь данных

1. `load_table` читает CSV/Parquet и возвращает DataFrame без исправления
   содержимого.
2. `load_config` проверяет YAML; неправильная конфигурация останавливает вызов
   как ошибка API.
3. `validate_schema` определяет совместимые признаки. Ошибка одного признака не
   отменяет расчёт остальных.
4. `check_quality` проверяет обе таблицы, ничего не удаляя из входа.
5. Drift-модули получают только признаки с корректной схемой. Затем единая
   BH-коррекция принимает решения по KS/χ².
6. Если ML-блок включён, `adversarial_validate` строит OOF-предсказания только
   по допустимым и не исключённым признакам.
7. `pipeline.analyze` собирает схему, качество, drift, ML, алерты и сводку;
   `json.dumps(..., allow_nan=False)` служит инвариантом результата.
8. Streamlit читает готовый словарь. UI не пересчитывает тесты; отдельно строит
   только график выбранного распределения по тем же входным таблицам.

## Короткое объяснение методов на данных проекта

| Метод | Что показывает | Пример seed 42 |
| --- | --- | --- |
| KS | Максимальный разрыв эмпирических CDF; p-value зависит от размера | Сдвиг age: `D=0.2702`, BH `q≈3.67e-48` |
| Wasserstein | Средняя «стоимость переноса» в единицах признака | Age: `0.38 → 8.25` лет |
| PSI | Логарифмический индекс по общим ячейкам со сглаживанием | Age: `0.015 → 0.456` |
| JS divergence | Симметричная ограниченная divergence, база 2 | Age: `0.0027 → 0.0786` |
| χ² | Разницу наблюдаемых и ожидаемых категориальных частот | Region: BH `q≈1.38e-34` |
| Adversarial | Насколько LightGBM различает источник строки на OOF | Контроль `0.494`, combined `0.726` |

Ни один из этих сигналов без актуальной целевой переменной не доказывает
concept drift или снижение качества основной модели.
