# Совместная работа

Команда: Михаил и Павел. Дедлайн проекта — 27.09.2026; календарные задачи сейчас заданы только на 07.09–13.09.

## Ветки

- `main`: общая основа и принятые изменения.
- `mikhail`: рабочая ветка Михаила, план `docs/plans/mikhail.md`.
- `pavel`: рабочая ветка Павла, план `docs/plans/pavel.md`.

Ветки начинаются от одного общего коммита. Оба плана доступны в каждой ветке. Наличие двух планов в `main` помогает видеть зависимости; каждый отмечает выполнение прежде всего в своём файле.

После подключения GitHub перед началом работы обновлять свою ветку:

```bash
git fetch origin
git switch mikhail
git merge origin/main
```

Павел использует `git switch pavel`. Команды выполняются при сохранённых локальных изменениях. Незавершённые изменения сначала коммитятся в свою ветку.

## Правила изменений

1. Делать небольшой законченный шаг и проверять его на содержательном примере.
2. Коммитить код вместе с тестами поведения и коротким описанием результата.
3. Отправлять свою ветку и открывать pull request в `main`.
4. Напарник проверяет интерфейс, смысл результата и воспроизводимость.
5. После принятия PR обновлять рабочую ветку из `main`. Персональные ветки сохранять, не удалять автоматически после merge.

`contracts.py`, `docs/contracts.md` и общий формат конфигурации меняются по согласованию. Владельцем `pipeline.py` является Павел, владельцем правил drift-алертов — Михаил. Проверки качества Павел возвращает в том же формате результатов.

При конфликте не перезаписывать чужую реализацию целиком: сравнить обе версии и сохранить необходимые изменения. Избегать принудительной перезаписи общей истории.

## Ежедневная отметка

В конце дня в своём плане записывать: выполненное, ссылку на commit/PR, результат проверки и конкретный блокер. Если задача не завершена, так и отмечать; не выдавать заглушку за готовую функцию.

Датасеты, секреты, окружения и тяжёлые результаты в Git не добавляются. Числа в документации должны происходить из выполненного эксперимента.
